# ADR-0014: UUIDv7 ids and per-user ownership keys

## Status
Accepted

## Date
2026-11-27

## Context
One install may host several people (§3), and HTTP and MCP hand record ids to clients and agents. The
spec left the id type to the builder (§6.4). It asks that every query be scoped by user, and that the
database act as the second lock behind the use cases.

## Decision
- **Ids are UUIDv7**, generated by Postgres (`uuidv7()`, built in since 18). In Go they are a
  `domain.ID` value type with a strict parser: a malformed id is `id.invalid`, a 400 at the doors.
- **Every owned table carries `user_id`.** A child references its parent through
  `(parent_id, user_id) → parent(id, user_id)`, and every parent has `unique (id, user_id)`. Postgres
  then refuses a row that mixes two users, even when a use case forgets a check.

## Alternatives considered
- **`bigint` identities:** shorter in MCP responses, but sequential ids reveal how much other people on
  the same install write.
- **UUIDv4:** random, so inserts scatter across the index.
- **Scoping only through the parent's `user_id`:** fewer columns, but a forgotten join filter leaks data,
  and a tag of one user could label another user's movement.

## Consequences
- Ids are 36 characters in responses.
- Scoping is a plain `where user_id = $1` on every table.
- Cross-user rows fail on a foreign key, which the repositories report as not found.
